핵심 요약

최종 판단은 “실제로 악용 가능한 중대한 취약점이었으나, 대규모 현장 침해까지 확인된 것은 아니며, 알려진 핵심 결함에 대한 패치의 기술적 타당성은 강하게 확인되지만 모든 실서비스의 적용 완료는 확인할 수 없다”이다.

CVE-2024-6387은 인증 전에 실행되는 OpenSSH 서버의 신호 처리 경쟁 상태다. 공격에 성공하면 특정 Linux 환경에서 root 권한의 임의 코드 실행까지 이어질 수 있다. Qualys는 2024년 7월 1일 32비트 Debian/glibc 환경에서 이를 실제로 입증했다. 그러나 그 실험에는 장시간의 반복 시도와 타이밍 제어가 필요했고, 그 결과를 64비트 전체 또는 인터넷 공개 서버 전체의 공격 난이도로 일반화할 수 없다. [S1]

이 문제는 2006년에 수정했던 신호 처리 안전성 문제가 2020년 코드 리팩터링 과정에서 다시 나타난 회귀(regression) 사례다. OpenSSH 9.8p1은 신호 처리 중 안전하지 않은 로그 출력을 제거하고 시간초과 로그를 정상 실행 문맥에서 처리하도록 수정했다. Debian·Ubuntu와 RHEL 계열은 기존 버전에 더 작은 변경을 적용해 같은 직접 원인을 차단했다. 공개된 수정 소스에 대한 정적 분석 결과는 설득력이 높다. [S2][S3][S7][S8][S10]

이 보고서에서 공격 성공 실험, 공개 공격 도구 또는 스캔, 실제 침해 사건, 패치 패키지 배포, 개별 서버의 패치 설치는 별도로 취급한다. 하나의 관측 수치를 다른 범주의 성과로 바꾸어 주장하지 않는 것이 평가의 핵심 원칙이다.

1. 조사 범위와 판정 방법

분석 범위는 2026년 10월 11일까지 확보한 공개 자료다. 주요 대상은 Linux에서 실행되는 OpenSSH Portable의 sshd이며, 운영체제의 libc 구현, 배포판 백포트, 서비스 실행 방식에 따라 위험이 달라질 수 있다는 조건을 유지한다. OpenBSD나 모든 Unix 계열을 동일 취약성으로 취급하지 않는다.

증거는 세 수준으로 구분했다. 첫째, 발견자의 직접 실험, 개발사의 공개 소스와 공식 보안 공지처럼 결함 또는 수정 내용을 직접 보여주는 자료다. 둘째, 특정 시점의 보안업체 독립 시험과 인터넷 관측 자료다. 셋째, 공격 동향에 대한 언론·보안업체의 주장이다. 후자의 경우 실제 사고의 성공 여부를 확인할 수 있는 별도 근거가 없다면 추정으로 남긴다.

조사 과정에서는 OpenSSH 9.7p1과 9.8p1의 관련 코드 경로, Debian·Ubuntu 백포트 패치, CentOS 9 계열 공개 패치, 배포판 보안 공지와 테스트 스크립트를 대조했다. 패치된 전체 실행 파일을 직접 검증하거나 취약점 익스플로잇을 자체 실행하지는 않았다. 이러한 검증 수준의 차이는 본문과 결론에 반영한다.

2. 기술적 원인: 어떻게 취약점이 되살아났는가

2.1 인증 제한시간과 비동기 신호

OpenSSH 서버는 클라이언트가 정해진 시간 안에 인증하지 못하면 연결을 종료한다. 당시 기본 LoginGraceTime은 120초였다. 시간초과 시 발생하는 SIGALRM은 평상시 코드의 어느 지점에서든 실행을 중단시키고 등록된 신호 처리기를 호출할 수 있다.

문제의 OpenSSH 9.7p1에서는 sshd.c의 grace_alarm_handler()가 시간초과 상황에서 sigdie()를 호출한다. 이는 log.c의 sshsigdie()와 sshlogv()로 이어져 로그를 출력한다. 그런데 로그 출력 경로에는 syslog() 및 그 내부 메모리 관리처럼 비동기 신호 처리 문맥에서 안전하다고 보장되지 않는 함수가 관여할 수 있다. [S1][S2]

공격자는 시간초과 신호가 이미 진행 중인 glibc 메모리 관리 연산을 끊도록 반복적으로 타이밍을 맞춘다. 신호 처리기에서 같은 계열의 비안전 함수가 재진입하면 내부 상태가 훼손될 수 있다. 즉 취약점은 단순한 인증 실패나 시간초과 오류가 아니라, 비동기 실행 문맥에서 실행해서는 안 되는 코드가 호출된다는 설계 문제다. 타이밍 조건이 맞아야 하므로 연결 하나만으로 반드시 성공하는 공격은 아니다.

2.2 2006년 수정에서 2020년 회귀까지

OpenSSH는 2006년 CVE-2006-5051에 대응하면서 DO_LOG_SAFE_IN_SIGHAND 보호 조건을 사용해 신호 처리 중 위험한 로깅을 우회했다. Qualys가 분류한 4.4p1부터 8.4p1까지의 구간에는 이번 회귀 문제가 존재하지 않는다. 이 말은 해당 오래된 버전이 모든 보안 취약점에서 안전하다는 뜻은 아니다. [S1]

2020년 10월 로깅 코드 리팩터링 커밋 752250c에서는 해당 보호 조건이 제거됐다. 그 결과 OpenSSH Portable 8.5p1부터 9.7p1까지에서 신호 처리기의 안전하지 않은 로깅 경로가 다시 활성화됐다. 코드 변경과 취약 버전 경계가 일치한다. 2025년 8월 개발자 Damien Miller도 관련 병합 과정에서 Portable 전용 보호 코드가 누락된 사람의 실수였다고 설명했다. 이를 고의적인 백도어로 볼 증거는 없다. [S1][S4][S5]

소결: 원인과 발생 경위에 대한 근거 신뢰도는 높다. 경쟁 상태를 유발하는 호출 경로와 해당 보호 조건이 제거된 코드 이력이 직접 확인된다.

3. 위험 평가: 실험에서 성립한 공격과 실제 침해

3.1 Qualys가 무엇을 입증했는가

Qualys는 2024년 7월 1일 Linux/glibc 기반 OpenSSH에서 인증 없는 원격 코드 실행을 발표했다. 특히 Debian 12.5 i386 가상머신과 취약한 OpenSSH 9.2p1 패키지를 대상으로 ASLR이 활성화된 조건에서 root shell 획득에 성공했다. [S1]

공개 실험에 기술된 공격은 짧고 안정적인 단발 공격과는 달랐다. 해당 환경에서는 경쟁 상태를 유리하게 만들기 위해 평균 약 1만 회의 시도가 필요했고, 이 단계에 대략 3~4시간이 걸렸다. ASLR이 적용된 glibc의 주소 추정까지 포함해 root shell을 확보하는 데는 평균 약 6~8시간이 보고됐다. 동시 연결 수, LoginGraceTime, 지연과 대상 구성에 따라 이 값은 달라진다. 따라서 6~8시간은 특정 실험의 결과이지 모든 미패치 서버의 공통 침해 시간은 아니다.

NVD의 CVSS v3.1 기본점수는 8.1점(High)이다. 공격 복잡도는 높게 평가되면서도 인증·사용자 상호작용 없이 네트워크에서 접근할 수 있고 성공할 경우 기밀성·무결성·가용성에 큰 영향을 미칠 수 있음을 반영한다. 점수는 위험의 성질을 평가한 것이지 실제 피해 건수를 측정한 값은 아니다. [S6]

3.2 64비트 환경에 관한 정확한 표현

Qualys가 최초 공개 시점에 성공을 입증한 것은 특정 32비트 환경이다. 당시 64비트 amd64에서의 동일한 원격 root 코드 실행을 실증했다고 해석해서는 안 된다. 2025년 8월 Damien Miller는 자신이 파악한 범위에서 64비트 시스템의 성공적인 exploit을 아직 알지 못한다고 설명했다. [S5]

이 진술은 2025년 당시 개발자의 지식 범위를 나타낼 뿐, 2026년까지 64비트 공격이 불가능했다는 증명은 아니다. 반대로 32비트 실험의 성공만으로 모든 64비트 배포판에서 같은 비용으로 공격이 가능했다고 주장할 수도 없다. 실증 환경과 잠재 영향 범위를 구분해야 한다.

3.3 공개 PoC, 야생 공격 주장, 독립 검증의 차이

Palo Alto Networks Unit 42는 2024년 7월 2일 기준 실제 악용을 알지 못한다고 밝혔고, 당시 유통된 공개 PoC를 자체 시험했지만 원격 코드 실행은 재현하지 못했다고 보고했다. 이 실패는 Qualys의 별도 실험 성공을 뒤집지 않는다. 사용한 코드, 시스템 조건, 공격 정밀도가 다를 수 있기 때문이다. 다만 공개 PoC의 존재만으로 누구나 실전 공격에 성공할 수 있었다는 주장도 지지되지 않는다. [S7]

같은 시기 일부 보안업체는 실제 환경에서의 악용을 주장했다. 하지만 검토한 사례에는 공격 스크립트 공개, 스캔 대상 목록, Shodan 분류 등이 주요 근거로 제시됐고, OpenSSH 7.4처럼 이번 8.5p1~9.7p1 회귀 영향 범위 밖의 버전도 대상에 포함됐다. 그 자료만으로 CVE-2024-6387을 통한 root 권한 탈취가 특정 서버에서 성공했다는 포렌식 결론을 낼 수 없다. [S8]

2024~2026년 검토한 공개 근거에서 신뢰할 만한 성공 침해의 전체 건수나 대규모 실제 침해 사건은 확증하지 못했다. 이는 실제 피해가 0건이라는 뜻이 아니다. 공개되지 않은 사고와 관측하지 못한 공격 가능성이 남는다. CISA KEV에 관한 일부 2차 추적 자료도 참고했으나 공식 최신 전체 목록을 독립적으로 전수 대조하지 못했으므로 미등재를 결정적 근거로 사용하지 않는다.

소결: 실험상 root RCE는 사실이며 영향은 중대하다. 다만 공격 구현 난이도와 실제 성공 침해의 공개 증거 부족 때문에 “즉시 대규모 침해가 발생했다”는 표현은 뒷받침되지 않는다.

4. 패치의 기술적 유효성과 후속 취약점

4.1 OpenSSH 9.8p1: 비안전 로깅을 신호 처리 밖으로 이동

OpenSSH는 2024년 7월 1일 9.8p1을 발표하며 해당 신호 처리 경쟁 상태를 수정했다. 확인한 소스에서는 9.7p1의 grace_alarm_handler()가 sigdie()를 통해 로그를 남겼던 것과 달리, 9.8p1의 sshd-session.c가 제한시간 종료 시 직접 _exit(EXIT_LOGIN_GRACE)를 사용한다. 부모 sshd 프로세스의 child_reap()는 자식 종료 상태를 해석한 뒤 정상 실행 문맥에서 시간초과 로그를 기록한다. [S2][S3][S9]

이 방식은 공격자가 노리는 신호 처리 중 로깅 함수의 위험한 재진입을 구조적으로 없앤다. 일시적인 LoginGraceTime 확대나 공격 성공 확률 감소와 달리, 알려진 직접 원인을 제거하는 수정이라는 점에서 타당성이 높다.

4.2 Debian·Ubuntu·RHEL: 작은 백포트로 같은 직접 원인을 차단

주요 배포판은 대규모 upstream 변경을 구버전 패키지에 그대로 이식하기보다 기존 sshsigdie()에서 sshlogv()를 호출하는 부분을 컴파일에서 제외했다. Debian 12와 Ubuntu 22.04의 공개 패치는 va_list 처리와 sshlogv() 호출을 #if 0과 #endif로 감싸고, 그 뒤의 _exit(1)은 남겨둔다. 이는 Qualys가 공개적으로 제안한 최소 패치와 부합한다. [S1][S10][S11]

CentOS 9 계열 공개 패치에서도 해당 최소 변경을 확인했다. 다만 검토한 파일은 후속 보완까지 반영된 공개 소스이므로 Red Hat이 2024년 7월 3일 배포한 최초 RPM의 바이트 단위 내용과 같다고 주장하지 않는다. 배포 공지는 Red Hat의 별도 공식 문서로 확인했다. [S12][S13]

두 수정 계열은 보안 목적이 같아도 모든 동작이 동일하지 않다. 최소 백포트는 신호 처리기에서 이전에 남기던 오류 로그를 생략하지만, 9.8p1은 부모 프로세스에서 시간초과를 기록한다. 그러므로 “원래 취약점의 직접 원인을 차단한다”와 “기능까지 완전히 동일하다”는 별개 명제다.

4.3 CVE-2024-6409는 왜 별도로 다뤄야 하는가

RHEL 9 계열에서는 또 다른 신호 처리 문제가 CVE-2024-6409로 보고됐다. 이는 권한이 분리된 비특권 자식 프로세스가 신호 처리 중 cleanup_exit()를 호출하는 경로와 관련된다. 공개된 후속 패치에서는 해당 부분을 _exit(255)로 바꿨다. Red Hat은 6387 수정 공지와 별개로 2024년 7월 10일 6409에 대한 수정 공지를 제공했다. [S12][S14]

두 CVE에는 “신호 처리 중 안전하지 않은 함수 호출”이라는 공통 교훈이 있지만 실행 경로와 권한 문맥이 다르다. 따라서 6409의 발견이 6387에 대한 기존 root RCE 패치가 작동하지 않았다는 직접 증거는 아니다. 반면 코드베이스 전체의 신호 처리 안전성을 넓게 점검할 필요가 있었다는 반론은 유효하다.

OpenSSH 9.9 변경 기록에는 9.8에서 빠졌던 감사 로그 이벤트를 복원한 내용도 있다. 보안 수정에 기능적 회귀가 전혀 없었다고 단정할 수 없지만, 이것 역시 6387 root RCE가 재발했다는 증거로 혼동해서는 안 된다. [S15]

4.4 무엇을 테스트했고 무엇은 테스트하지 않았나

OpenSSH 9.8p1에는 login-timeout.sh라는 회귀 테스트가 있다. LoginGraceTime을 짧게 설정해 연결을 시간초과시킨 뒤 다른 SSH 연결이 가능한지 확인하는 기능 테스트다. 이 테스트의 존재는 서비스 동작 확인에 의미가 있으나, 경쟁 상태를 통한 메모리 손상이나 root RCE의 불가능성을 독립적으로 증명하지는 않는다. [S16]

본 조사는 소스 코드 경로를 정적으로 대조했으며, 직접 패키지를 빌드하거나 공격 재현·배포판별 전체 회귀 시험을 수행하지 않았다. 따라서 정적 검증 결과는 “알려진 핵심 결함 제거에 관한 강한 근거”이고, 모든 실행 환경의 무결성을 입증한 최종 동적 검증은 아니다.

소결: upstream 수정과 주요 배포판의 백포트는 알려진 CVE-2024-6387의 직접 원인을 차단한다고 평가할 충분한 코드 근거가 있다. 후속 CVE와 기능적 차이는 별도 관리해야 한다.

5. 보안 수정 배포와 실제 운영환경의 잔존 위험

5.1 배포판은 실제로 언제 수정했는가

대상최초 공개·수정 기준의미

Debian 12(Bookworm)2024-07-01, 1:9.2p1-2+deb12u3구버전 기반 백포트 제공

Debian의 DSA-5724-1, Ubuntu의 USN-6859-1, Red Hat의 RHSA-2024:4312로 각 수정이 공개됐음을 확인했다. Debian 11, Ubuntu 20.04, RHEL 8 등의 이전 기반 버전은 이번 2020년 회귀의 영향 밖이라는 배포판별 분류를 별도로 고려해야 한다. Amazon Linux 2023에도 수정 공지가 있었으며 Amazon Linux 1·2는 구버전 사용으로 이번 회귀에 영향받지 않는 것으로 분류됐다. [S13][S17][S18][S19]

이 표의 버전은 2024년 최초 수정의 기준 버전이다. 2026년 현재 설치할 권장 패키지의 최신 버전을 뜻하지 않으며, 운영자는 해당 배포판의 현재 보안 저장소와 공지를 우선해야 한다. 특히 sshd 배너 또는 upstream 버전 번호에 8.9p1이나 9.2p1이라고 표시된다는 이유만으로 취약하다고 판정하면 배포판 백포트를 누락할 수 있다.

5.2 “수백만 대 취약”이라는 수치는 무엇을 센 것인가

2024년 공개 직후 관측된 숫자는 상당히 컸지만, 조사 방법과 분모가 같지 않았다.

출처와 시점발표 수치측정 대상·판단 한계
Palo Alto Unit 42/Xpanse, 2024년 7월약 700만인터넷에 노출된 OpenSSH 가운데 영향 upstream 버전 범위로 식별된 인스턴스. 패치 백포트·운영체제 조건을 모두 확인한 수가 아님
Qualys, 최초 2024년 분석1,400만 이상Censys·Shodan 기반의 잠재 영향 서버 추정. 인터넷 공개 배너 및 식별 방식의 제약 존재
Qualys 고객 기반 관측, 최초 2024년 분석약 70만, 표본 중 약 31%Qualys의 글로벌 고객 CSAM/EASM에 속한 인터넷 공개 OpenSSH 인스턴스 가운데 취약 분류된 수. 전 세계 인스턴스의 31%를 의미하지 않음

Unit 42는 총 약 2,300만 개의 인터넷 공개 OpenSSH 인스턴스를 관측한 가운데 영향 버전 범위로 약 700만 개를 분류했다. 이는 배포판 백포트와 libc·설정·아키텍처의 실제 공격 조건을 확인한 검증된 취약 호스트 수가 아니다. Qualys의 1,400만 이상 추정 및 약 70만 고객 관측값과도 조사 대상이 다르므로 같은 시계열이나 분모로 합칠 수 없다. [S7][S20]

또한 2024년 이후 동일 모집단의 OS·패키지 수정·서비스 실행 상태까지 검증하는 비교 가능한 장기 측정 자료를 확보하지 못했다. 따라서 이 초기 수치로 2026년의 미패치 서버 수, 전 세계 패치율, 감소율을 계산하지 않았다.

5.3 배포와 적용의 마지막 간극

벤더가 수정 패키지를 제공했다는 것은 해당 버그에 대한 수정본을 구할 수 있다는 뜻이다. 그러나 관리자가 이를 설치했는지, 구버전 sshd 프로세스가 계속 실행 중인지, 접근 제한이 어떻게 구성됐는지까지 보여주지는 않는다. 정확한 현장 점검에는 패키지 전체 버전·릴리스 문자열과 보안 변경 이력, 실행 중 서비스 상태, 노출 경로가 필요하다.

소결: 주요 배포판의 신속한 패치 공개는 입증됐으나, 2026년의 실제 운영 시스템 전체가 수정됐다고 확인할 근거는 부족하다.

6. 주요 반론의 검토

반론 1. “실전 공격에 몇 시간이 걸렸으므로 위협을 과장했다.”
공격의 반복 비용과 실패 가능성은 현실적 악용 빈도를 낮출 수 있다. 그러나 인증 없는 원격 root 실행이 성공한 실험 자체를 없애지는 못한다. 공격 복잡도는 높고 잠재 피해도 높다는 양면 평가가 정확하다. [S1][S6]

반론 2. “수백만 대가 위험했으므로 이미 대규모 침해가 발생했다.”
인증 서비스의 외부 노출, 취약해 보이는 배너 버전, 공개 PoC, 공격 트래픽은 서로 다르다. 이번 조사에서 실전 root 탈취를 뒷받침하는 개별 사고의 신뢰할 만한 자료가 충분히 확인되지 않았다. Unit 42의 공개 PoC 재현 실패 결과와 야생 공격 주장에 포함된 비영향 버전 분류는 이 차이를 잘 드러낸다. 성공 침해 0건이라고 단정할 수는 없다. [S7][S8]

반론 3. “64비트 exploit이 공개되지 않았으므로 사실상 안전했다.”
2024년의 실증 범위와 2025년 개발자의 파악 범위에는 제한이 있다. 미실증은 불가능성의 증명이 아니다. 반대로 32비트 결과를 모든 64비트 환경에서의 성공 사실로 확장할 수도 없다. [S1][S5]

반론 4. “CVE-2024-6409가 뒤이어 나왔으니 최초 패치는 실패했다.”
후속 발견은 관련 코드 안전성 감사의 중요성을 보여주지만, 별도 권한 분리 경로의 문제를 6387의 패치 무효로 등치할 수 없다. 핵심 패치가 막는 정확한 코드 경로를 기준으로 평가해야 한다. [S12][S14]

반론 5. “보안 공지가 나왔으니 현재도 문제없는 상태다.”
백포트 제공과 운영 중인 서버에서 새 바이너리가 실행되는 것은 다르다. 패키지 배포가 확인됐다는 사실만으로 전체 인프라의 패치 성공률을 추정할 수 없다. [S10][S13][S17][S18]

이 반론들을 함께 고려해도 기본 판정은 바뀌지 않는다. 취약점의 기술적 실재성, 현장 공격 규모의 불확실성, 패치 코드의 타당성, 적용 완결성의 미확인이 동시에 성립한다.

7. 운영상 대응과 최종 결론

이미 유지보수 중인 시스템에서는 배포판의 보안 공지를 기준으로 수정된 OpenSSH 서버 패키지를 설치하고, 설치된 패키지의 릴리스 번호와 운영 중인 sshd 프로세스가 새 바이너리를 반영했는지 확인해야 한다. SSH 관리 포트는 가능한 한 관리망·VPN·허용된 출발지로 접근을 제한한다. 단순 ssh -V 결과나 네트워크 배너의 upstream 버전만으로 패치 여부를 판단하지 않는다.

긴급하게 패치를 적용하지 못할 경우 LoginGraceTime을 0으로 설정하는 완화 방안이 논의됐지만, 인증 제한시간 해제로 미인증 연결이 누적돼 MaxStartups 관련 자원 고갈·서비스 거부 위험이 증가할 수 있다. 이는 신중한 단기 대응일 뿐 정식 패치의 대체가 아니다. [S1]

최종적으로 CVE-2024-6387은 코드 리팩터링의 작은 보호 조건 누락이 치명적인 권한 경계 문제를 되살릴 수 있다는 사례다. 알려진 취약한 경로를 제거한 업스트림 패치와 주요 배포판 백포트는 기술적으로 타당하며, 공개된 근거만으로 이 원래 경로에 대한 패치가 실패했다고 말할 이유는 없다. 동시에 실제 공격 성공 규모와 2026년 미패치 시스템 수를 신뢰할 만한 숫자로 제시할 수 없으므로 “대규모 실전 악용”과 “현장 패치 완료”도 단정하지 않는다.

최종 종합 판정: 위험성은 높았고 기술적 패치는 알려진 직접 원인에 대해 유효했다고 판단된다. 다만 실제 피해 규모와 개별 운영 시스템의 패치 적용 완결성은 확인되지 않았다. 이 조건부 결론이 현재 근거에 가장 충실하다.

부록 A. 취약·수정 코드 경로 요약

부록 B. 배포판·관측 수치의 해석 원칙

수정 패키지의 전체 epoch·upstream·배포판 release는 함께 읽어야 한다. 예를 들어 Debian 12의 9.2p1, Ubuntu 22.04의 8.9p1, RHEL 9의 8.7p1 같은 상위 버전 숫자는 모두 9.8p1보다 낮지만, 보안 백포트가 적용된 패키지를 자동으로 취약하다고 볼 수 없다. 반대로 버전 번호가 적절하다고 해도 실행 중 서비스가 아직 교체되지 않았다면 운영 수준의 확인이 남는다.

초기 노출 통계는 서로 다른 관측 범위와 탐지 기준을 사용했다. 버전 범위에 속하는 인터넷 공개 인스턴스 수는 exploit 성공 건수도, 현재 취약 시스템 수의 직접 측정도 아니다. 특히 Qualys 고객 기반의 약 31%는 해당 고객 표본의 분모를 가진 수치다. 이 연구에서는 분모가 맞지 않는 값으로 세계 패치 적용률이나 시간 경과에 따른 감소율을 산출하지 않았다.

부록 D. 남은 불확실성 및 재평가 조건

현재 확인되지 않은 정보는 2024~2026 실제 성공한 침해의 전체 건수, 2026년 전 세계 미패치·실제로 악용 가능한 SSH 서버 수, 배포판별 실행 바이너리의 동적 무결성 검증이다. 중요한 반례가 추가될 경우 전체 조사를 반복하기보다 관련 주장만 우선 재평가해야 한다. 특히 신뢰할 수 있는 개별 사고 포렌식, 64비트에서의 독립 공격 성공 실증, 수정 패키지의 동일 경로 재발, 동일 모집단으로 측정한 실제 패치율 자료가 결론 변경의 조건이다.

실전 피해가 확인되면 현장 악용 평가를 높여야 하고, 반대로 재현 가능한 폭넓은 64비트 보호·빌드 검증 자료가 발표되면 적용 범위 평가를 정교화할 수 있다. 근거가 추가되지 않는 한 현재의 조건부 판정을 유지한다.
